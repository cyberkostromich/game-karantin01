## 2. Архитектура

### 2.1 Принцип
**Симуляция отделена от представления.** Вся игровая логика — в `sim/` и работает только с данными (позиции, HP, состояния). Узлы `Node3D` в `view/` лишь отображают состояние симуляции. Это даёт:
- хост считает симуляцию, клиенты только рисуют снапшоты;
- зомби — не узлы, а строки в массивах (Structure of Arrays) → тысячи без просадки;
- можно гонять симуляцию headless в тестах.

### 2.3 Тик симуляции (хост, 20 Гц, фиксированный)

```
1. Commands.apply(queued_commands_for_tick)
2. GameClock.advance()                     # фаза дня, события
3. NoiseSystem.collect() → ZombieSystem.on_noise()
4. WaveDirector.update()                   # спавн пачками
5. FlowField.update_dirty_sectors()        # если стены/здания изменились
6. ZombieSystem.update()                   # FSM + движение + атаки
7. UnitSystem.update()                     # таргетинг, огонь, способности
8. CivilianSystem.update()                 # FSM, работа, заражение-таймеры
9. BuildSystem.update()  TechSystem.update()
10. Economy.update()                       # непрерывная добыча; списания на рассвете
11. Combat.resolve_damage()                # единая очередь урона → смерти → спавн зомби из обратившихся
12. FogOfWar.update() (каждый 4-й тик)
13. Net.maybe_send_snapshot() (каждый 2-й тик)
```

## 3. Ключевые системы

### 3.1 Зомби: Structure of Arrays
```gdscript
# ZombieSystem.gd (фрагмент-контракт)
var count: int
var pos: PackedVector2Array      # XZ в метрах
var vel: PackedVector2Array
var hp: PackedFloat32Array
var type_id: PackedByteArray     # индекс в zombies.json
var state: PackedByteArray       # idle/investigate/chase/attack/horde/feeding
var target_id: PackedInt32Array  # -1 нет цели
var timer: PackedFloat32Array
var free_list: PackedInt32Array  # переиспользование слотов
```
- Движение: желаемая скорость = flow-field (horde) / вектор к цели (chase/investigate) / случайное блуждание (idle) + **разделение** через SpatialHash (3–6 ближайших соседей).
- Рендер: `MultiMeshInstance3D` на каждый тип; трансформы пишутся одним `set_buffer` за кадр. Анимация — vertex shader (покачивание + шаг по фазе), позже VAT.
- LOD: дальше 80 м от камеры — без разделения, апдейт FSM каждый 2-й тик.

### 3.2 Пути
- **Зомби:** flow-field на сетке 2 м, сектора 32×32. Цели: (а) Штаб для орды, (б) кэш до 8 «точек шума», живущих 20 с. Пересчёт только «грязных» секторов, когда строится/рушится стена. Стена — непроходима, но имеет «стоимость атаки»: если путь закрыт, flow-field ведёт к ближайшей стене (зомби ломают).
- **Военные и мирные:** `NavigationServer3D` (навмеш города запекается заранее, постройки — динамические obstacles) + RVO avoidance. Лимит ~250 агентов.
- **Техника:** тот же навмеш с большим радиусом агента; дороги дешевле (скорость on-road/off-road по `navgrid`).
- **Вертолёт:** без пути, прямая + высота 25 м.

### 3.3 Шум
```gdscript
NoiseSystem.emit(pos: Vector2, radius: float, source_team: int)
```
Раз в тик буфер шумов проходит по SpatialHash: idle-зомби в `radius * hearing_mult` → `investigate(pos)`. Крупные шумы (≥100) регистрируют точку в кэше flow-field целей.

### 3.4 Заражение
- Таймер инкубации хранится у мирного/юнита. По истечении: юнит удаляется, в той же позиции `ZombieSystem.spawn(walker | walker_armored)`.
- `is_infected` скрыт от клиентов до детекта (КПП/медик/симптомы) — снапшот клиентам не шлёт флаг заранее (анти-чит и честный сюрприз).

### 3.5 Экономика
- Добыча — реальные рейсы рабочих (узел ↔ здание), но настроены так, чтобы в среднем давать `yield_per_worker_per_day`.
- Энергия: каждые 0.5 с считаем баланс; при дефиците отключаем по приоритету (GDD §5).
- Рассвет: еда, мораль, рождения, взросление детей, отчёт ночи (событие UI).

### 3.6 Туман войны
Общий для команды. Сетка 4 м, `PackedByteArray` (0 — не открыто, 1 — открыто, 2 — видно сейчас). Обновление каждые 4 тика по кругам видимости. Клиентам шлём только изменения (RLE).

## 4. Сеть

### 4.1 Модель
- **Host-authoritative.** Хост = игрок, создавший лобби; на нём крутится `sim/`.
- Клиенты шлют **только команды** (RPC `reliable`), хост применяет их на ближайшем тике.
- Хост шлёт **снапшоты** 10 Гц (`unreliable_ordered`), клиенты интерполируют с задержкой 100 мс.
- События (смерть, постройка, исследование, рассвет) — отдельные `reliable` RPC.

### 4.2 Команды (контракт)
```json
{ "t": "move",     "pid": 1, "units": [101,102], "pos": [120.5, -40.0], "queue": false, "amove": false }
{ "t": "attack",   "pid": 1, "units": [101], "target": 5021 }
{ "t": "ability",  "pid": 2, "unit": 207, "ability": "flare", "pos": [300.0, 12.0] }
{ "t": "build",    "pid": 3, "building": "wall_wood", "cells": [[10,4],[11,4],[12,4]], "rot": 0 }
{ "t": "train",    "pid": 1, "building_id": 9, "unit": "sniper", "count": 1 }
{ "t": "assign",   "pid": 4, "civilians": [55,56], "building_id": 12 }
{ "t": "research", "pid": 2, "building_id": 14, "tech": "silencers" }
{ "t": "power",    "pid": 1, "building_id": 20, "on": false }
{ "t": "transfer", "pid": 1, "units": [101], "to_pid": 2 }
{ "t": "ping",     "pid": 3, "kind": "help", "pos": [80.0, 22.0] }
```

### 4.3 Снапшот (бинарный, на клиента)
| Блок | Формат | Размер |
|---|---|---|
| Заголовок | tick u32, фаза дня u8, время u16 | 7 Б |
| Ресурсы | food/wood/iron u16, power i8, morale u8, people u16×3 | ~14 Б |
| Зомби (в зоне интереса клиента, ≤ 600) | id u16, x i16 (дм), z i16 (дм), type u4+state u4, hp u8 (%) | 8 Б × N |
| Юниты/мирные (все) | id u16, x i16, z i16, rot u8, hp u8, state u8, owner u4 | 9 Б × N |
| Изменения тумана | RLE | переменно |

600 зомби × 8 Б × 10 Гц ≈ 48 КБ/с на клиента — укладывается в домашний аплинк хоста на 3 клиента (~150 КБ/с). Зона интереса = экран клиента + 40 м.

### 4.4 Лобби MVP
Прямой IP (порт 24680) + LAN-обнаружение (UDP broadcast). Слоты 1–4, выбор доктрины и цвета, кнопка «Готов». Хост стартует.

### 4.5 Дисконнект
Юниты отключившегося → ИИ «держать позицию». Переподключение по тому же нику в течение 5 минут возвращает контроль.

## 6. Ассеты: правила импорта

- 1 ед. = 1 м, Y вверх, pivot — центр основания, модели смотрят в **+Z** (конвенция glTF). В Godot включить «use model front» при импорте или повернуть корень на 180° вокруг Y.
- Все модели используют один материал `palette` (текстура 256×256, 16×16 цветов, UV в центры ячеек). Плейсхолдеры в пакете уже так устроены.
- Анимируемые части — отдельные узлы с именами: `turret`, `barrel`, `rotor_main`, `rotor_tail`, `arm_l`, `arm_r`, `leg_l`, `leg_r`, `head`, `weapon`. Пивоты частей — в точке вращения.
- Цвет команды — через шейдер-параметр `team_color` по маске (повязки/флажки помечены ячейкой палитры `TEAM`, см. `docs/05_art_bible.md`).

## 8. ADR (журнал решений)

| # | Решение | Альтернативы | Почему |
|---|---|---|---|
| ADR-1 | Godot 4.6 + GDScript | Unity 6 DOTS, Unreal, Three.js | Бесплатно, текстовые сцены для агентов, достаточно для 1–2 тыс. зомби через MultiMesh |
| ADR-2 | Host-authoritative + снапшоты | Детерминированный lockstep | Lockstep требует fixed-point и полного детерминизма — дорого для MVP. 4 игрока × 600 зомби в снапшоте укладываются в канал |
| ADR-3 | Зомби = SoA, не узлы | Node на зомби | Узлы сломаются после ~300 штук |
| ADR-4 | Город из OSM | Ручная сборка из Kenney City Kit | Реальная Москва дешевле, чем ручной левел-дизайн. Kenney — для пропсов и плейсхолдеров |
| ADR-5 | Один палитровый материал | PBR-текстуры на модель | Стиль low-poly + батчинг + лёгкий пайплайн для ИИ-генерации ассетов |
| ADR-6 | Москва (Лужники), не Лондон | Лондон | OSM одинаково хорош для обоих; Москва даёт идентичность и аудиторию, а река + мосты + арена дают готовый левел-дизайн |
